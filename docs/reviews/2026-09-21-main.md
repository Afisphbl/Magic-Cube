## Summary
This change expertly introduces the core 54-sticker permutation logic and the Zustand state machine. The pure mathematical model for the 18 face turns is robust, and the single-move input buffer and scramble queue effectively satisfy the ACs. However, there is a major issue where the move counter and history erroneously record scramble moves as part of the player's solve session.

## Major
### 🟠 Scramble moves are tracked in the player's move counter and history, `src/store/useCubeStore.ts:211`
**Problem**: In `finishMoveAnimation`, when an animation completes, `moveCount` is incremented and `moveHistory` is appended regardless of the `gamePhase`.
**Why it matters**: A scramble sequence (e.g., 20 moves) will artificially inflate the player's move count and pollute their move history before the solve session even begins, breaking the core scoring metric.
**Suggested fix**: Only increment `moveCount` and append to `moveHistory` if the current `gamePhase` is `PLAYING` or `SOLVED` (transitioning to `PLAYING`). Note that you may also need to update the assertion in `test/cube_store.test.mjs` that explicitly expects `moveCount` to equal 20 after a scramble.

## Minor
### 🟡 Game ignores solved state when finishing a scramble, `src/logic/cubeMoves.ts:268`
**Problem**: In `getNextGamePhase`, when `currentPhase === 'SCRAMBLING'` and `hasPendingMoves` is false, it unconditionally returns `'PLAYING'`.
**Why it matters**: If a scramble sequence accidentally results in a solved cube, the game transitions to `PLAYING` instead of automatically recognizing the `SOLVED` state. The player would be stuck in `PLAYING` with a solved cube.
**Suggested fix**: In the `SCRAMBLING` branch, when `hasPendingMoves` is false, return `isSolved ? 'SOLVED' : 'PLAYING'`.

### 🟡 Duplicated store action logic, `src/store/useCubeStore.ts:160`
**Problem**: `applyMoveDirect` and `applyMoveAction` have exactly identical implementations.
**Why it matters**: Duplicating state transition logic creates maintenance overhead; future bug fixes or enhancements applied to one might be missed in the other.
**Suggested fix**: Remove `applyMoveAction` if it is unused, or have both actions call a shared internal helper function.

## Nits
- ⚪ `src/logic/cubeMoves.ts:192`, `combinePerm` applies `p2[p1[i]]` which is mathematically backward for `p1` then `p2`. It works flawlessly right now only because it's exclusively used for double turns (`p1 === p2`), but should be `p1[p2[i]]` for correctness.
- ⚪ `src/logic/cubeMoves.ts:234`, `isCubeSolved` allocates a new `Set` on every call. Since `validateCubeState` already guarantees exactly 9 of each color, tracking `seenColors` is redundant and can be removed to save allocations.

- `isCubeSolved` perfectly handles orientation invariance, freeing players from needing to align the cube to a specific global orientation.
